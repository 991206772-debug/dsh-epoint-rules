# Epoint Design TDD Coder

本 Skill 是纯提示词驱动的编码流程。工作单位是当前需求的完整 Story 集合，按业务连续性组织批次，不按单个文件申请任务。骨架完成后不调用 Epoint MCP 推进编码状态；当前 Coder 连续负责实现和验证，禁止再次调用本 Skill 或把批次转交另一个 Coder。

## 编码执行循环

用户启动编码后，按下列循环处理整个需求，不把一次工具调用、一项测试或一个批次当作当前轮的交付范围：

1. 从现有任务清单和原始 Story/AC 选择下一项可执行任务。当前批次仍有可做行为就继续当前批次；当前批次没有可执行项才展开下一批。局部缺少外部合同或运行条件的任务保留具体缺口，不阻止其他任务。
2. 只读该任务必要的验收、源码和规范，完成对应行为测试、业务实现及可运行验证。测试或编译失败先查具体错误并修复；排除文件后的编译只能报告实际覆盖范围，不能当作全量编译成功。
3. 业务结果变化时保存进展并简短展示当前任务与下一项可执行任务，然后回到第 1 步。下一动作必须是服务该任务的真实读取、测试或实现；不能用空调用、重复读取或只写“下一步做什么”代替施工。
4. 所有可执行工作完成后，按“交付”对照原始 Story/AC 自审；发现遗漏就重新打开原任务并回到第 1 步。只有自审后没有可执行工作，或所有剩余任务均有证据证明无法安全推进时，才进入最终回复，分别报告已完成和待外部条件验证的范围。

局部测试通过、数据库暂不可用、任务清单保存成功，均不是收尾条件。中途更新只报告实际进展及下一任务，更新后继续执行，不要求用户回复“继续”。真实授权 STOP、用户取消必须遵守；宿主实际中断按“压缩与恢复”保存可恢复信息。不能预判宿主将中断而主动收尾；上下文不足先缩小实现范围、保留必要证据，不伪造全局阻塞。

## 边界

- 只实现 Epoint 管理端和后端能力，不开发移动端、网站、小程序或 App 页面。
- 当前需求源码与对应测试均在授权业务范围内修改；可沿当前调用链读取其它模块源码，但不能据此扩大写入范围。保护既有行为，不顺手重构；保留公司注解、分层、页面绑定和工作流底座。
- 需求、设计、规则库、`design-tdd-plan.json/md`、`business-facts.json`、`relevant-rules.json`、`code-state.json` 和 Builder 凭证不得手写。不按业务文案拆改上游模块；用户明确反馈需调整上游时，按对应 Requirement/Design Skill 的原准备入口显式修订，由 Builder 更新资料。
- 本地实施任务清单是人读工作记忆，不是新状态机、门禁或用户逐批确认点。
- 普通实现缺口和可撤回的技术选择自行处理，依据和影响记任务清单。只有已确认资料无法回答、且会改变业务结果的事实冲突或必要外部合同，以及授权不清或不可逆操作才提问；保留受影响任务，继续其余可执行任务，不把局部缺口当成整需求停工。缺少可选查询工具不属于阻塞。

## 启动

已获得 `coderIntakeRef` 和 `implementationTasksPath` 时，直接读取现有资料。字段未保留时，从 `.active-demand` 定位 `code/requirement-work-draft.json`；文件符合 `requirement-work-draft-index/v3` 且骨架已完成时，直接把它作为 `coderIntakeRef`，从同级目录派生 `demand-implementation-tasks.md` 路径，不逐个扫描全部目标确认开工。

只有 intake 不存在或无效时才调用 `design_tdd_build_plan`；骨架使用 `design_tdd_skeleton_materialize`，不自行拆分目标或扫描目录猜进度。返回有剩余目标的 `skeleton_partial` 时，按返回的同入口下一步继续，成功文件会跳过；失败项按具体原因定向修复，不重答整个设计。骨架首次完成返回 `stopAfter=true/awaitingUser=true` 后立即停止，等待用户启动编码；已完成的骨架不重跑。

编码中收到反馈，原需求不变的实现遗漏直接增量修代码；改变需求或设计则由对应 Skill 显式修订并同步，再读取更新后的 intake 和受影响 Story/事实。既有源码交给 Coder 增量调整，不用模板覆盖；只有新增目标走骨架。保留任务编号和未完成项，将受影响的已完成任务重新打开，继续实施，不因反馈额外要求逐批确认。修订不授权数据库变更、部署或删除旧代码。

v3 入口通过 `storyCatalogRef` 提供全部 Story 描述、AC 编号与场景、`detailRef`；`targetIndexRef` 和 `readCatalogRef` 提供按需导航，不在入口内嵌全部代码文件。首次计划前只读 intake 和全部功能目录，保留全部 Story/AC 的覆盖关系，不预读全部验收正文、骨架、Plan、facts、规则或实践。当前任务再读其 `detailRef` 的完整要求。当前资料出现 `contentRefs/nextRef` 或纯 `contentRef` 续页时读至末尾；规则和实践菜单中带标识、适用条件及 `contentRef` 的条目先选择，再完整读取选中正文，不递归展开全部菜单引用。不能把目录或第一页当成全文，不自行编写命令重整资料。已有进度则走“压缩与恢复”。

## 当前批次取证

1. 根据全部功能目录建立 Story/AC 覆盖表，按连续业务组织批次；只展开当前批次，不从摘要重新制定验收。当前 Story 的 `detailRef` 提供完整 AC、不变量、目标与事实引用。共享文件的 `storyIds` 和 `storyBindings` 一起使用；通过 `carriedByModuleId/carriedByEntityKey` 找承载方，不能为被承载 Story 重造独立骨架。`accessByStoryId` 是读写导航，不限制在 `authorizedWriteRoots` 内新增必要业务源码。
2. 建立或更新任务清单，把当前批次标记为 `active`，按“任务清单与可见进度”展示 TodoList。读取当前 Story 的 `targetRefs`、`businessFactRefs` 直接事实及 `ruleMenuRefs`、`practiceMenuRefs` 菜单；按当前行为选择正文和 `resourceRefs`。`relatedFactRefs` 是关联参考，验收涉及其中对象、联动或既有行为时再展开，不因共享物理模块就全读其它 Story 资料。目标内的 `useWhen`、`queryOnly` 和 `dataAccessPlanRef` 提供用途及查询资料，不另读逐文件指导卡。只按当前行为补读 `globalFactRefs` 中归属未明确的事实，不能认定这些事实可省略。需要其它导航时再读 `readCatalogRef`：`commonRefs` 与当前 Story/module/fileKind/feature 的并集是候选导航，不是全文必读清单。`afterBatchRef` 在批次验证时读取，不提前全读。
3. 修改目标前核对当前源码的类声明、继承、依赖、相关方法签名，以及当前调用链的方法体、回调和调用方；区分已实现行为与空骨架，不只看方法名或 TODO。只读当前关联源码，大文件定向读取，但不能省略影响当前行为的方法体。已有导航直接使用，不另建临时索引或检查脚本反复整理整个施工包；`design-tdd-plan.json` 仅在导航或承载信息不足时定向读取。规则切片是菜单，不能代替正文。规则按能力、版本和适用条件选择；实践卡先判断当前行为是否满足 `useWhen`，成立后读取 `contentRef` 正文并执行其中适用的 `required`，不把同文件类型下全部卡当必读；卡片漏列必要规范时允许定向补读。源码已有能力及待补缺口记进度，不从文件清单推断完成。资源 ID 永远使用原有稳定 ID，禁止加 `B1:` 等批次前缀。
4. 已读资源 ID 随任务进展或批次统一保存，不要求每读一个文件立即重写清单；中断前保存恢复所需信息。选中正文后沿续页读完整；宿主截断时使用其分段读取能力续读缺失部分，不把截断内容当全文。缺失路径先核对清单和已知来源，不猜路径；可选导航缺失可定向检索，必需业务事实缺失不能编造。“读到了”看相关正文是否实际可见，“用对了”看源码及对应验证是否落实，不新增阅读确认表。

本地复用卡内的 `blocked/errorCode` 只描述该导航卡缺少索引，不等于当前编码阶段被阻断；不得据此认定项目没有实现。`repair_required` 表示本次工具调用未执行：按返回的合法动作同轮修正并继续；`repair_current_coding_patch` 表示当前 patch 未执行，按错误中的规则修正后同轮重新写入。不要求用户确认、不重启编码；工具误用不得变成重新制定计划。真正的阶段阻断、越权或 STOP 仍按其合同处理。

### 技术不确定性查证顺序

本顺序适用于整个 Vibe Coding 的所有批次和压缩恢复，不是要求每个问题机械调用所有工具。先复用任务清单中仍适用于当前产品、版本和源码的证据，再按以下来源逐层查证：

1. **规则证据 / `rule_expert`。** 先看当前 Story 的 `ruleRefs` 和 `rules.<fileKind>` 的 `ruleMenuCards`，按当前行为、适用条件和版本选正文；`ruleRefs.path` 与规则卡中 `ruleRefs[].filePath` 是规则原文来源，`contentRef` 是卡片正文，不等于已读其中引用的原文。公司实践按当前机制定向读取 [company-common-mechanisms.md](references/company-practices/company-common-mechanisms.md)，不全文预读。按 `sourceFile` 及 `reuse` 中 `services[].sourcePath`、`actionPath/directCalls[].sourcePath/relatedEntities[].sourcePath` 核对实际 API。本地规则正文已足够时不重复调用 MCP；路径无效或缺正文时，用 `rule_expert(action="read")` 读已知规则，规则名不明确时先 `action="search"` 再读全文。此工具只查公司规范，不代替项目源码核实；Coder 不调用 `rule_expert(action="analyze/execute")`，也不走 `team_rules_search`。
2. **CodeGraph 与当前工程源码。** 对项目内类、方法和调用链，优先用 CodeGraph 按精确符号定位定义、调用方和候选文件，再读取命中的当前源码核实签名与行为。CodeGraph 不可用、未安装、索引过时或无命中时，不等待、不阻断：对类名、方法名、实体或调用方做一次本地定向源码搜索；禁止全工程无目标扫描。CodeGraph 是导航，不替代当前源码。
3. **Nextbot（相关工具资料中也写作 Nexbot）。** 仅当本地规则和当前工程源码不足、且产品已有源码可能回答当前技术问题时，才查询产品源码。已知类名/方法名用 `search_symbol`；没有精确符号时用 `search_code`。产品和版本必须取自真实项目事实；返回路径只作产品源码来源说明，不是当前工程路径，也不能覆盖公司规则或当前工程源码。
4. **精确后备核实。** 前三层仍无法确认某个必要外部 API 时，才对具体类/方法做一次定向签名核对；能先写出最小实现的，优先让聚焦编译给出具体错误，再按错误定向核对。禁止循环解包、遍历大量 Maven JAR 或重复查询同一事实。编译只验证类型与调用，不证明业务行为完成。

每次只查当前实现切片所需的事实。**查证结束条件：**Story/AC 行为已明确、目标源码已读、直接适用规则正文已读、本次已有 API 签名已有证据；满足后下一动作必须写对应行为测试或业务实现，测试先行后立即实现对应行为。当前批次已确认接口规则时，没有项目调用样例也按规则实现；新增业务方法按验收要求命名并在 ServiceApi/ServiceInternal/ServiceImpl/调用方闭合，不搜索尚不存在的方法。后续遇到新接口、验收差异、编译/测试错误或源码/依赖变化时允许定向查证，不重复查已确认事实。每个来源对同一事实最多查一次；无结果就转下一来源，不据此断定依赖不存在，也不换关键词循环盲搜。

CodeGraph 或 Nextbot 未安装、未注册、不可用、超时或无结果时，只记录原因并继续使用其余证据和本地实现，不要求安装、不退回设计、不把批次标成 `blocked`。两者同时不可用也一样。只有必要外部合同仍无法安全确认时，才如实保留该具体实现缺口；工具缺失本身不是阻断理由。采用事实、来源和当前工程验证结果只记进度；源码/产品/版本未变化时恢复后复用，不重复研究同一签名。

不要求为每次方法调用读取完整 business-facts；需要专项业务事实时再读取目录登记的对应资源。

## 实现与验证

- `constructionBindings`中`bindingKind=configuration_only`表示现有平台配置交付，不是骨架缺失；不新开发字典管理、角色管理或菜单管理页面，不补表、Entity或Service。配置任务仍按原Story/AC保留任务编号和任务清单，并在交付说明现有章节列出所需代码项、角色访问范围和实际管理菜单入口；门户页面不注册管理菜单。未实际配置或未验证权限时写“待配置/未验证”，文档生成不代表配置完成，不因此暂停其他开发。其他业务Story的字典引用、权限限制及拒绝行为仍须实现和验证。
- 骨架是施工起点，不代表需求已完整实现，也不保证生成结果没有错误。原需求明确需要管理端页面时，先核对既有页面的入口、表单对象、可编辑范围及调用参数是否真正适合承载，不能只因“已有表单”就认定可用；优先复用，确实不适合时可在授权业务目录内按公司路径、命名与交互规范补必要 HTML、Action 和业务方法，不等待另行确认。被承载 Story 在承载模块中补齐，不重造业务模块、表或 Entity；不能因新增文件不在 `targetIndex` 就停工。新增页面、职责和验证结果记任务清单。
- 先区分已有 API 调用和新增业务方法。已有公司/项目/第三方 API 按“技术不确定性查证顺序”核对签名与获取方式，复用已确认能力，不重写代码项、附件、会话等底层实现；调用已有API的业务Story仍要完成页面绑定、保存、权限拒绝及联动，不能因为API存在就标成配置完成。来源不明或版本不适用时保留具体缺口，不凭名称猜签名，继续其他可执行任务。新增业务方法、辅助变量、成员字段或类可以由当前验收要求产生，在授权范围内实现并验证，不要求它们事先出现在骨架或 API 清单。
- 持久化字段仍来自已确认表设计或真实实体，不擅自新增数据库字段；已有方法大小写、参数、返回值不凭印象改写。新增 Service 方法同步闭合 ServiceApi、ServiceImpl、ServiceInternal 及调用方。
- 主从、多表的整体保存必须保证全部成功或失败回滚。按需读取 [GP-05 主从表和事务明细](references/company-practices/company-best-practice-dispatch.md#gp-05-主从表和事务明细)、[CM-05 事务](references/company-practices/company-common-mechanisms.md#cm-05-事务)，按公司规则和真实 API 确认实现方式。没有事务注解示例只代表写法尚未确认，不能省略事务、改成逐条保存或把保存前的独立删除当作整体保存；纯只读不要求事务。必要技术事实仍无法确认时，将具体缺口留在进度，继续其他可执行任务，不编造 API 或降低业务要求。
- `queryFilters` 中 `implementation=coder` 是关联筛选的待实现行为：按已确认的输入、目标字段和 `relationPath` 实现关联查询及分页/计数，验证匹配和不匹配结果；骨架输入框和AI_TODO不代表查询已完成，不把关联字段当主表条件或删掉筛选。
- 按当前任务读取目标段落再 patch，优先做通该业务结果，不先铺开所有页面再铺开所有后台；必要依赖允许调整顺序，保留缺口并继续其他可执行任务，不要求前一任务全部验证通过才能动下一项。不重复撰写方法级改动说明；编辑后检查改动及 import、类声明、括号边界。页面只检查本次受影响的绑定、调用和参数，一个可验证业务结果完成后再做完整检查，不每次 patch 重跑整套清单。改 Java 时按 [backend-rules-checklist.md](references/backend-rules-checklist.md) 的通用 Java import 要求检查。
- 验证失败（含真实编译报告的类型错误或依赖缺失）先读取首个具体错误及对应报告，再按原因修复并重跑受影响检查。本需求测试因源码调整而失效时，核对原验收并修复或迁移测试；来源不明的旧测试和用户改动保留，不直接删除。没有新证据时不重复同一失败命令、不轮换猜测或清理构建产物；清理必须针对已确认的产物问题，不能将疑似环境原因写成每批必做操作。只有容器、数据库或外部服务缺少运行条件时，保留待验证范围并执行其余可运行检查和任务，不以局部测试代替集成验证。不按编辑次数停工，可继续的其他批次不因局部问题全部停下。
- 按原验收保留前置条件、操作结果、拒绝场景和跨模块联动；沿实际入口、处理、持久化及后续结果核对需求涉及的环节，不把“自动”改成“手工”、把组合条件减成单项。对业务逻辑和状态转换补真实单测/集成测试，页面核对前后台调用闭合；联动须验证接收方结果，不能只改发起方状态。
- 批次完成前读取 `readCatalog.afterBatchRef` 的自检资料，执行当前命中的 backend/frontend checklist 和 feature bridge；只读详情不要求保存、删除或导出。检查本批 TODO、假数据和 diff：区分骨架指导注释与真实待实现事项，后者必须实现或保留为缺口，不能批量删标记当作完成。
- 逐条对照原始 Story/AC 和既有行为，记录实现位置、验证命令、退出码、首个错误及未覆盖项，再按“编码执行循环”更新进展和选择任务。零项测试（`Tests run: 0`）不算验证通过，不能用 `failIfNoTests=false` 证明业务已验证；校验、解析测试通过不代表数据库保存、失败回滚或页面交互已验证。方法存在、CRUD 齐全、TODO 删除或编译通过也不能单独作为业务完成依据。

工作流页面保留隐藏回调锚点、`uc-handlecontrols` 和 `workflowjsboot.js`，操作按钮来自流程配置；不改 Design XML。禁止引入 Vue、React、ElementUI、JPA、MyBatis、Lombok 或其它脱离项目的框架，不改平台目录或敏感配置。

## 任务清单与可见进度

只维护 `<demandDir>/code/demand-implementation-tasks.md`，将任务要求和实际结果保存在同一记录中；它是人读工作记忆，不是机器真值。文件顺序为：

1. **当前工作与下一步**：目标、排除项、当前批次、下一任务编号和最后一个真实错误。
2. **全部功能和批次覆盖**：全部 Story/AC 的批次归属、依赖及既有行为保护点；只展开当前批次，其他批次标注“待展开”。
3. **未完成及待验证任务**：包括延后或依赖未满足的任务，保留缺口、批次和下一步。
4. **已完成任务**：实际实现及对应验证支持完成结论的任务。
5. **必要技术证据**：已确认接口签名、适用版本、来源和已读资源 ID；未确认的推测保留为待确认事项，不能当作已确认事实。只保留必要引用，不复制完整需求、规则、源码或工具输出。

两个任务区域采用同一紧凑格式：

```markdown
- [ ] T001 <业务结果>（<Story/AC 引用>）
  - 要求与验证：<必要条件、结果、拒绝或失败处理>
  - 位置与规则：<实现位置、适用规则引用>
  - 实际进展：<实现情况、验证程度、证据>
  - 缺口与下一步：<未完成行为及后续动作>
```

- 任务编号 `T001、T002…` 在需求内唯一，新任务按最大编号续号；换批次、延期、恢复或重新打开时不改编号。每项对应可验证业务结果，不按文件、按钮或技术层机械拆分。同一任务可覆盖多个 AC，但列出全部引用，保留允许、拒绝、回滚及跨模块结果；原文没有 AC 编号时引用 Story 和小节，不修改上游补编号。
- 直接继承已确认需求和设计，不重新拆 Story、制定验收或解释整份需求。要求与验证写简短行为、实际条件和预期结果，不只写“编译”或“测试”。
- 每个任务只保留一处当前结果；完成或重新打开时移动记录，不复制矛盾状态。实现情况沿用“未实现/已实现”，验证程度沿用“未验证/静态确认/编译通过/对应测试通过”；验证证据只支持其覆盖的行为，未覆盖项仍是缺口。只有实际实现和对应验证支持完成结论时才勾选 `[x]`；代码已写但未验证、零测试或仅编译通过的业务任务仍保留缺口，配置说明不代表已配置。
- 开工、任务实际进展变化、批次切换或重要缺口出现时，展示当前批次 TodoList 和已完成、进行中、待处理、待验证任务数；仅统计已展开任务，每项只计一次，不当作工期或需求还原百分比。宿主提供原生待办工具时使用它，任务标题保留编号，状态遵循宿主实际合同；没有工具时在对话输出 Markdown TodoList，不要求安装、不停止编码。面板和对话只是本地清单的展示，不另拆任务或维护第二套结果；恢复时从清单更新展示。
- 状态沿用 `pending / active / blocked / done / waiting`，最多一个批次 `active`。真实错误改变下一步时更新；业务结果变化、批次切换或中断前统一保存，不要求每次读取、每个 patch 都更新。仍有未实现行为时不能标批次 `done`；局部依赖或环境不能验证时保留具体缺口，继续其余可执行任务，不增加门禁或逐项确认。新验证覆盖旧失败的当前结论；源码或依赖变化后允许重新查证。
- 已有任务清单优先使用；只有旧计划 `demand-implementation-plan.md` 和进度 `demand-implementation-progress.md` 时，Coder 在下一次继续编码时一次性合并，保留编号、要求、证据、批次和缺口；旧文件保留但不再维护。缺编号的旧记录补唯一编号，不重新施工。程序不解析或自动迁移 Markdown，不新增过程文件、固定重读次数或停止钩子。

## 压缩与恢复

上下文不足时按“编码执行循环”缩小实现范围，把缺口和必要证据写入任务清单；保存后仍选择下一项可执行任务。压缩摘要保留 `implementationTasksPath`、当前批次编号、`coderIntakeRef` 路径、最后一个真实错误，以及任务编号、未完成行为和下一步，不复制整个规则库。不因切换批次或上下文恢复额外要求用户确认；若宿主实际中断，如实说明中断和续做位置，不把它标成业务阻塞或声称必定自动续跑。

恢复先读任务清单中的当前工作与未完成及待验证任务，再按任务编号读取该任务要求、原始 Story/AC、intake 导航及必要源码和规范，不重新分析整个需求。核对每个缺口的后续安排并同步可见 TodoList，不因它属于先前批次就忽略。压缩后允许按需重读已读规则章节、方法签名和被当前任务依赖的已完成批次接口；“已读”不等于内容还在上下文中。

从功能目录找到当前 Story 的 `detailRef`，已生成目标按 `targetRefs` 的 `storyIds/storyBindings` 找 `resolvedPath`，必要时补读 `targetIndexRef`。清单中的实际变更路径记录施工事实，不代替已生成目标导航；Coder 新增页面及源码从原任务记录的实现位置定位，再核对公司路径和当前调用方，不因 targetIndex 未列出就丢弃缺口或重复新增。允许顺着当前调用链查证相关源码，不因它不在 targetIndex 就禁止读取；写入范围不扩大。不因压缩重做已完成工作；新证据推翻已完成结论时，重新打开对应任务及批次，沿用编号并移回未完成区域，只修受影响行为。没有 active 时按清单选择下一 pending 批次或报告真实阻塞；清单缺失则据原始要求、旧记录及实际产物重建，不重新物化骨架。

## 交付

重新读取原始 Story/AC，逐项核对实际源码和测试，不只检查自己的清单或完成总结；任务全部完成、TodoList 全部勾选也不能替代原始 Story/AC 的需求核验。检查页面 `initPage/action/execute/bind` 与后台闭合、公司分层和版本桶、真实 diff、TODO 与敏感信息；将遗漏重新登记并继续实现，必要外部依赖无法解决的如实报告，不能擅自改称交接来宣告完成。运行项目聚焦测试和完整编译/测试；环境不支持时明确降级为静态确认，不声称已编译通过。

代码验证后自审 `<demandDir>/delivery/generated/交付说明.md`：确认文件存在、非空，且按实际产物写成实现稿（待评审）；已有设计稿不能仅改标题就算实现稿。`delivery/交付说明.md` 等其他位置的文件只读参考，不算正式交付文件，不覆盖 `delivery/manual/**`。

若有有效的 Coder 阶段 `delivery/.runtime/documentation-task-card.json`，按卡内 `deliveryFactsRef`、`inputRefs` 和模板精确路径取证，只写卡内允许的 `delivery/generated`。卡片缺失或生成失败时，使用编码阶段已有的已确认的设计、实际 SQL 路径、实际源码和验证记录，按 [delivery-summary-template.md](assets/delivery-summary-template.md) 补写或修订正式交付说明；不重造受管事实或文档卡，不重跑设计和编码，也不为填文档在工程中盲搜。设计与实际不符时以实际产物为准，差异和证据不足处写清楚。

文档中区分“未涉及”“未发现”“未生成”：有 SQL 文件但没有执行凭证时写“已生成、未执行”，没有实际测试结果时写“未验证”；路径、配置值和验证结论不能猜。写后重读正式文件，核对七个固定章节、模板占位、实际 SQL/页面/配置与验证结论；有工作流时按模板第 8～10 节核对流程配置、事件和外部方法主记录及参数明细，方法以实际源码为准，XML 只读引用，缺少事实写“未登记”。

满足“编码执行循环”的结束条件后，最终交付或报告真实阻塞时，分别报告代码 `done/blocked/waiting`、交付文档“已生成/待补”、完成内容、验证结果和限制，不遗留 active；这项收尾要求不用于中途保存恢复信息，不能为了结束当前轮次伪造完成或阻塞。文档生成或自审失败只报告原因和下一步，不回退已完成的代码状态，也不能把缺文档说成整体交付完成。
